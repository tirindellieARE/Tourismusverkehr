# Script Map

What every script in this folder reads, writes, and does. Paths are relative to
`RScript/tourists/` unless noted. Scripts are grouped: the active pipeline
(numbered `01`–`04` plus `aggregate_regions.R`, stays in `tourists/`), and
everything no longer used to produce a result in `README_results_trajets_Ausland_CH.md` —
legacy one-off model runs (pre-EMU, superseded by `04_destination_choice.R`)
and ad-hoc analysis/debug scripts — which live in `old/`.

## Data directory layout

`data/` is split into three parts:

- **`data/input/`** — raw files, not produced by any script. The bare-minimum set needed to start from scratch (see the list at the bottom).
- **`data/output/`** — intermediary files: produced by one script, read by another. Everything here is fully reproducible by re-running `01` → `02` → `03` in order.
- **`data/final_output/`** — reserved for files that are terminal results, not read by any script. Currently unused/empty: every file `data/` holds today is either a raw input or something a later script still reads. The actual final results (model estimates, coefficient tables) live in the separate top-level `results_output/` folder, not under `data/`.

`data/amr101.gpkg` and `data/erreichbarkeit_tt2023.gpkg` live at the `data/` root rather than under `input/` or `output/` — they're raw inputs (used by `aggregate_regions.R`) but predate the `input/`/`output/` split and were left in place rather than moved, since moving them would have required re-checking every path that reads them. Anything else in `data/` not referenced by any script (old survey extracts, unused shapefiles, etc.) was also left in place at the `data/` root.

## Core pipeline

`03_estimate_logsum.R` was split in two: `03_estimate_logsum_Ausland_CH.R` (foreign-entry trips, feeds the tourist destination choice models below) and `03_estimate_logsum_CH.R` (domestic CH -> CH trips, documented in `README_trajets_CH_CH.md` -- not yet consumed by any other script).

Run `01` → `02` → `03_estimate_logsum_Ausland_CH.R` → `04_destination_choice.R` for the zone-level destination choice model. For the AMR-region variant, `aggregate_regions.R` is NOT script "05" in that same sequence — it must run BEFORE `04_destination_choice_amr.R` (which reads its output), despite being listed after `04_destination_choice.R` below since it also depends on `03_estimate_logsum_Ausland_CH.R`'s logsum output: `01` → `02` → `03_estimate_logsum_Ausland_CH.R` → `aggregate_regions.R` → `04_destination_choice_amr.R`. `03_estimate_logsum_CH.R` only needs `01` → `02` (for `tt_CH_CH.fst`) plus `data/output/mc15.csv`, and is not part of either of those two chains.

### `01_agent_generation.R`
- **Reads**: `data/input/Finale_Auswertungsdatenbank_AGQPV2015_V2.csv` (raw AGQPV 2015 survey), `data/input/zones_communes.gpkg`
- **Writes**: `data/output/agqpv.csv`, `data/output/agents.csv`
- **Does**: filters the raw survey to foreign-origin, Switzerland-destined leisure trips (`STARTORTLANDISO != "CH"`, `ZIELORTLAND == 1`, `FAHRTZWECK == 5`); renames columns; spatially joins origin/destination/residence coordinates to traffic zones; joins destination zone topology (`STALAN2020`) and, for each of the three zone types, the zone's country (`origin_zone_country`, `dest_zone_country`, `residence_zone_country`, from `zones_communes.gpkg`'s `MAKROBEZ_STAAT` column: `"CH"` / `"LI"` / `"Ausland"`) -- a sanity check that `origin_zone`/`residence_zone` are genuinely abroad and `dest_zone` is in Switzerland. A consistency filter then drops observations that contradict "foreign tourist entering Switzerland": `origin_zone_country == "CH"` (27 obs), `dest_zone_country != "CH"` (27 obs), or a `nationality`/`residence_zone_country` mismatch (3 obs -- `nationality == 1` implies residence should be `"CH"` and vice versa; likely a residence coordinate geocoded just across the border). 54 obs dropped in total (3 matched more than one criterion), 22,097 -> 22,043; writes `agqpv.csv`. Then replicates rows by survey weight (÷1000 scaling) to build a synthetic expanded population, `agents.csv`.
- **Note**: one zone in `zones_communes.gpkg` (`NO` 910000000) has an empty geometry and no attributes at all, including no `MAKROBEZ_STAAT` -- dropped before zone assignment.
- **Note**: `agents.csv` is produced here but not consumed by any other current script except the debug script `old/tmp_omx_inspect.R`.

### `02_build_tt_lookups.R`
- **Reads**: `data/output/agqpv.csv`, `data/input/zones_communes.gpkg`, `data/input/TTC.omx`, `data/input/RITA.omx`, `data/input/EGT.omx`, `data/input/ACT.omx`, `data/input/TT_FGV.omx`, `data/input/TT0_VELO.omx`, `data/input/MIV_KOS.omx`, `data/input/OEV_KOS.omx`, `data/input/DIS_MIV.omx`, `data/input/DIS_VELO.omx`, `data/input/DIS_OEV.omx`
- **Writes**: `data/output/tt_agqpv.fst`, `data/output/tt_ausland_CH.fst`, `data/output/tt_CH_CH.fst`
- **Does**: builds car (`tt_miv` = TTC), PT (`tt_oev` = RITA+EGT+ACT), foot (`tt_fgv` = TT_FGV), bike (`tt_velo` = TT0_VELO) travel times, car cost (`cost_car` = MIV_KOS), PT cost (`cost_pt` = OEV_KOS), and three distance measures -- bike-route (`dist` = DIS_VELO), car-network (`dist_miv` = DIS_MIV), PT-route (`dist_pt` = DIS_OEV) -- from the OMX matrices. `tt_agqpv`/`tt_ausland_CH`/`tt_CH_CH` share the same destination side (Swiss zones only, `MAKROBEZ_STAAT == "CH"`, ~7,966 -- none of the three ever needs an Ausland/LI zone as a destination), and their `tt_miv`/`tt_oev` columns are derived from one bulk travel-time computation (origin = every real zone, CH or abroad, ~8,718, x destination = the ~7,966 CH zones), sliced three ways: `tt_agqpv` = only the origin-destination pairs that actually occur in `agqpv.csv` (10,886 rows); `tt_ausland_CH` = every zone abroad (`MAKROBEZ_STAAT != "CH"`, i.e. "Ausland"/"LI", 752 zones) x every Swiss zone -- the candidate universe the destination choice model needs (foreign entry point -> Swiss destination); `tt_CH_CH` = every Swiss zone x every other Swiss zone (63.5M rows). `tt_CH_CH` additionally gets `tt_fgv`/`tt_velo`/`cost_car`/`cost_pt`/`dist`/`dist_miv`/`dist_pt` (~2.9GB total) -- TT_FGV.omx/TT0_VELO.omx/OEV_KOS.omx/DIS_VELO.omx/DIS_OEV.omx cover all 7,966 CH zones but only 13/752 abroad zones (MIV_KOS.omx/DIS_MIV.omx cover all zones, but are kept CH-only too for consistency), too little abroad coverage to be useful for `tt_agqpv`/`tt_ausland_CH`. Consumed by `03_estimate_logsum_CH.R` (domestic mode choice).
- **Note**: `dist` (DIS_VELO, bike route) is highly correlated with `tt_fgv`/`tt_velo` (r ~ 0.986) since foot/bike times are themselves ~constant-speed transforms of that same network distance -- not usable as a distance control in foot/bike's own utility (caused a singular/non-converging model in `03_estimate_logsum_CH.R` when tried). `dist_miv`/`dist_pt` are less extremely correlated with their respective mode's own travel time (r ~ 0.96 car, ~0.947 PT) and are used as distance controls for car/PT there.
- **Note**: the master travel-time table (8,718 origins x 7,966 destinations = ~69.4M rows) is built with ONE bulk 2D read per OMX matrix (`h5file[["data/…"]][row_index_vector, col_index_vector]`), not a loop over origin zones. An earlier version looped origin-by-origin (~8,718 individual single-row HDF5 reads); at that scale it did not complete in over an hour and was killed -- HDF5 chunk/compression overhead makes thousands of small scattered reads far slower than one large hyperslab read. Verified the two approaches return identical values on a random test slice before switching.
- **Note**: OMX encodes "no path found" / unreachable OD pairs with a sentinel travel time of 999999 per leg (so a fully-unreachable PT trip, `tt_oev = rita+egt+act`, sums to 2,999,997). Converted to `NA` per matrix (`mat_ttc`, `mat_rita`, `mat_egt`, `mat_act` each individually, threshold >= 900,000) right after the bulk read, so `tt_miv`/`tt_oev` are `NA` rather than a huge fake travel time. This matters because car and PT are not always unreachable together: of the 5,990,432 `tt_ausland_CH` rows, 238,980 have car unreachable and 167,471 have PT (any leg) unreachable, but only 167,286 have *both* unreachable -- the other ~71,700 need the reachable mode's real travel time preserved, not discarded. Fed raw into the mode-choice utility (before this fix), sentinel values produced logsum values as extreme as -3,695 for the pooled model instead of the normal ~[-2, 1.5] range -- see the matching note in `03_estimate_logsum_Ausland_CH.R` below for how `compute_logsum()` handles the resulting per-mode `NA`s.
- **Note (correction)**: an earlier version of this note claimed TT_FGV/TT0_VELO/MIV_KOS/OEV_KOS/DIS_MIV/DIS_VELO/DIS_OEV needed no sentinel handling, based on a spot-check of only 300-500 of 7,966 zones that happened to miss the affected ones. A full scan found the sentinel (>= 900,000) IS present: 15,930/63,457,156 `tt_CH_CH` rows for `tt_fgv`/`tt_velo`/`dist` (e.g. destination zone 834202072 has `tt_fgv = 12,765,945`, `tt_velo = 999999`), and 170 rows for `dist_pt`; `cost_car`/`cost_pt`/`dist_miv` are genuinely clean (0 sentinel rows). Discovered while validating `03_estimate_logsum_CH.R`'s pooled+topology model -- the untouched sentinel values were blowing up the EMU logsum for the handful of affected zone pairs (max 13,944.8 instead of a sane ~137.9). Fixed by applying the same `>= 900,000 -> NA` conversion already used for `tt_miv`/`tt_oev` to all seven matrices.

### `03_estimate_logsum_Ausland_CH.R`
- **Reads**: `data/output/tt_agqpv.fst`, `data/output/agqpv.csv`, `data/output/tt_ausland_CH.fst`
- **Writes**: `results_output/mode_choice_model.rds` (+ `_tagesreise`/`_reisemitue`), `data/output/tt_ausland_CH_logsum.fst` (+ `_tagesreise`/`_reisemitue`) (+ Apollo's own per-model `results_output/mode_choice*_iterations.csv`, `*_output.txt`, `*_estimates.csv`)
- **Does**: estimates a binary MNL mode choice model (car vs. PT) on non-Swiss agqpv respondents' real origin→destination trips, using `border_mode` as the observed choice. Run three times: pooled (all non-Swiss), Tagesreise only (`n_nights == 0`), Reise mit Ü. only (`n_nights > 0`). For each, computes the EMU/logsum (`ln(exp(V_car)+exp(V_pt))`) for every OD pair in `tt_ausland_CH` (origin abroad × destination in Switzerland only -- the accessibility variable actually consumed by `04_destination_choice.R`) and saves it. Documented in `README_results_trajets_Ausland_CH.md`.
- **Note**: `results_output/mode_choice*.rds`, `*_iterations.csv`, `*_output.txt`, `*_estimates.csv` are Apollo's own artifacts in the top-level `results_output/` folder (untouched by the `data/` reorganisation).
- **Note**: `compute_logsum()` treats a `NA` `tt_miv`/`tt_oev` (mode unreachable, see `02_build_tt_lookups.R`'s sentinel-value note) as that mode's utility being `-Inf`, not as the whole OD pair being missing -- so a zone reachable by only one mode still gets a valid logsum equal to that mode's utility. Only OD pairs unreachable by *both* modes end up `NA` in the output (167,286 / 5,990,432 rows in `tt_ausland_CH_logsum.fst`).
- **Note**: was originally combined with what is now `03_estimate_logsum_CH.R` into a single `03_estimate_logsum.R`; split into two scripts since the domestic (CH -> CH) mode choice model has a different data source (`mc15.csv` vs. `agqpv.csv`), different alternatives (4 modes vs. 2), and no pooled/Tagesreise/Reise-mit-Ü. split.

### `03_estimate_logsum_CH.R`
- **Reads**: `data/output/tt_CH_CH.fst`, `data/output/mc15.csv`, `data/input/zones_communes.gpkg` (for destination-zone `STALAN2020` topology)
- **Writes**: `results_output/mode_choice_model_ch.rds`, `data/output/tt_CH_CH_logsum.fst` (MNL); `results_output/mode_choice_model_ch_nl.rds`, `data/output/tt_CH_CH_logsum_nl.fst` (nested logit, tree 1); `results_output/mode_choice_model_ch_nl2.rds`, `data/output/tt_CH_CH_logsum_nl2.fst` (nested logit, tree 2); `results_output/mode_choice_model_ch_nonlinear.rds`, `data/output/tt_CH_CH_logsum_nonlinear.fst` (Model 5, log+quadratic tt) (+ Apollo's own per-model `results_output/mode_choice_ch{,_nl,_nl2,_nonlinear}_iterations.csv`, `_output.txt`, `_estimates.csv`)
- **Does**: estimates a 4-alternative mode choice model (car / PT / foot / bike) on domestic revealed-preference trips from `mc15.csv` (`origin_zone`, `dest_zone`, `mode`), using each mode's travel time (`tt_miv`/`tt_oev`/`tt_fgv`/`tt_velo`), cost for car/PT (`cost_car`/`cost_pt`), and distance for car (`dist_miv`) from `tt_CH_CH.fst`. mc15's raw "walk" mode is relabelled "foot"; the small "other" category is dropped. Reference alternative: foot (`asc_foot` fixed at 0 by omission), the most common mode overall (65.5%). **Pooled model** (a distance-band-segmented version was tried and discarded -- see below) with each mode's travel-time coefficient interacted with urban/rural topology (`STALAN2020`, base = urban, shifts for hilly/mountain), keyed to the trip's **destination** zone (an origin-zone variant, Model 4a, was tried first and gave the same qualitative story with slightly worse fit -- see `README_trajets_CH_CH.md`). This spec (**Model 4b**) is estimated three times: once as a flat MNL (`apollo_mnl`), and twice as a **nested logit** (`apollo_nl`) under two different tree hypotheses, to test whether some modes' unobserved utility is correlated in a way IIA can't capture -- tree 1 = `{foot}` vs. `{car, pt, bike}` (walkable vs. not), tree 2 = `{foot, bike}` vs. `{car, pt}` (self-propelled/free vs. powered/priced). Every nesting parameter is reparametrized as `lambda = 1/(1+exp(-raw_lambda))` so the optimizer can never leave the RUM-consistent (0,1) range (an earlier unconstrained attempt on tree 1 converged to an invalid 3.14). With the constraint in place, ALL nesting parameters in both trees converge to their boundary (lambda -> 1, i.e. no nesting), and LR tests show no improvement over the flat MNL for either tree -- see `README_trajets_CH_CH.md`'s "Nested logit" section. **A fourth model (Model 5)** replaces Model 4b's single linear travel-time term and topology interaction with BOTH a log term (`log(tt+1)`) AND an hours-scaled quadratic term (`(tt/60)^2`) for every mode, and no topology at all -- this resolves the "wrong-sign" `b_tt_car`/`b_tt_pt` confound outright (both log coefficients come out correctly negative) and beats Model 4b on both AIC and BIC despite having fewer parameters (14 vs. 18) -- see `README_trajets_CH_CH.md`'s "Model 5" section. **Model 5 is now the recommended specification**, ahead of Model 4b; the nested logits remain informative negative results (no correlation structure found) but are not adopted either. Computes the logsum for every OD pair in `tt_CH_CH.fst` from each model's own formula (flat log-sum-exp for MNL and Model 5; each nested-logit tree's own inclusive-value formula for the two NL trees) and saves all four -- no Tagesreise/Reise-mit-Ü. split (`mc15` has no such distinction).
- **Note**: not yet consumed by any other script -- all eight output files (four `.rds`, four `_logsum*.fst`) are overwritten each time this script is re-run, so they always reflect the latest model version, not necessarily what's described in `README_trajets_CH_CH.md`'s earlier model(s).
- **Note**: Model 4b and Model 5 are NOT nested (different travel-time functional form, Model 5 has no topology interaction), so a chi-square LR test between them is invalid -- an earlier version of this script attempted one anyway and got a negative degrees-of-freedom and `NaN` p-value from `pchisq()` (silently, no error) since Model 5 actually has FEWER parameters than Model 4b (14 vs. 18). Fixed by comparing the two via AIC/BIC instead, which doesn't require nesting.
- **Note**: a distance-band-segmented version (split at `dist_miv` = 5km into "short"/"long" bands, fully separate model per band) was tried first and DID fix the "wrong" (positive) `b_tt_car`/`b_tt_pt` sign in the long band (>= 5km, 91.8% car, 99.5% of `tt_CH_CH`'s zone pairs) -- see `README_trajets_CH_CH.md`'s segmentation section for that full discussion. It was abandoned in favour of the current pooled + topology-interaction model per user direction; the topology interaction is a different, complementary lever (spatial heterogeneity in time-sensitivity) and does not itself fix the sign confound, which is still present in the current pooled model.
- **Note**: always write utility (`V`) expressions as a single static formula, never a runtime `if` branch on a closure variable -- a branch silently breaks Apollo's analytical-gradient pre-processing (falls back to slow, noisy numerical derivatives), which produced a spurious saddle-point convergence with `NaN` standard errors during the segmented-model work. Use `apollo_fixed` to hold a parameter at 0 instead of branching it out of the code; a static algebraic transform (like the logistic reparametrization used for `lambda_moto`) is fine and doesn't trigger this issue, since it's not a conditional branch.
- **Note**: a free (unconstrained) nesting parameter can converge outside the theoretically valid (0,1) range with no warning from the optimizer itself (only from Apollo's post-hoc RUM-consistency check) -- when that happens the whole coefficient vector tends to rescale along with it, and any LR test against a flatter model becomes meaningless. Always constrain a nesting parameter (e.g. via a logistic transform on an unconstrained underlying parameter) rather than estimating it freely.
- **Note**: with the constraint in place, a nesting parameter converging to its boundary (lambda -> 1) produces a singular BHHH matrix and an Apollo warning that "some parameter values may be tending to +/- infinity" (raw_lambda -> +Inf under the logistic transform) -- this is the expected, correct signature of "this nest genuinely collapses to flat MNL," not an estimation bug, and matches what happened for every nesting parameter tried in both trees above.

### `03e_carfoot_nonlinear_CH.R`
- **Reads**: `data/output/tt_CH_CH.fst`, `data/output/mc15.csv`
- **Writes**: `results_output/mode_choice_model_ch_carfoot_{linear,quadratic,log}.rds` (+ Apollo's own per-model `results_output/mode_choice_carfoot_{linear,quadratic,log}_iterations.csv`, `_output.txt`, `_estimates.csv`). No `tt_CH_CH_logsum*.fst` output -- see below.
- **Does**: a diagnostic sub-analysis, per request ("remove pt and bike and try non-linear specifications for walk and car travel times") -- a **binary car-vs-foot** MNL (PT/bike dropped from the choice set entirely; the sample is restricted to `mc15` trips where car or foot was the actual chosen mode, 8,180/8,730 trips), comparing three functional forms for travel time: **A. linear** (`tt`, minutes), **B. quadratic** (`tt/60`, hours -- see note), **C. log** (`log(tt+1)`, minutes). Cost and car-network distance are kept for car (same as `03_estimate_logsum_CH.R`'s base spec); topology interactions are left out to isolate the travel-time functional form. **Result: the log specification both fits best (AIC 5,131 vs. 5,554 linear / 5,371 quadratic, same 5 parameters as linear) and fixes the "wrong-sign" `b_tt_car` confound outright** (−1.557, correct sign) -- something none of the 4-mode models in `README_trajets_CH_CH.md` achieved without distance-band segmentation. Quadratic also flips the sign, but only past a 14-minute turning point. Documented in `README_trajets_CH_CH.md`'s "Car/foot binary choice, non-linear travel time" section. Does not compute a logsum -- a car/foot-only choice set isn't a valid stand-in for full 4-mode accessibility, so this script's results are diagnostic only, not (yet) fed into the production pipeline.
- **Note**: `tt_fgv` (walking time, used in the never-chosen alternative's utility too) reaches ~2,113 minutes (~35h) for some long-distance car-chosen trips -- a real network-distance value (Switzerland's diagonal is a very long walk), not a data error. Squaring that in MINUTES (~4.5M) overflowed the utility scale when combined with Apollo's small test perturbations of the starting values, crashing estimation ("Log-likelihood calculation fails at values close to the starting values"). Fixed by expressing the quadratic model's travel times in HOURS instead -- keeps every squared term inside a sane range. Model B's coefficients are per-hour, not per-minute like A/C.
- **Note**: an earlier version of this script factored utility (`V`) construction into a shared `build_V()` helper function called from inside each model's `apollo_probabilities()`, which silently broke Apollo's analytical-gradient pre-processor (same failure class as a runtime `if` branch, see `03_estimate_logsum_CH.R`'s notes -- "Apollo was not able to compute analytical gradients", falls back to slow numerical/finite-difference derivatives). Fixed by inlining each model's utility list directly inside its own `apollo_probabilities()`, with no indirection through an external function.

### `04_destination_choice.R`
- **Reads**: `data/output/agqpv.csv`, `data/input/zones_communes.gpkg`, `data/output/tt_ausland_CH_logsum.fst` (default; `data/output/tt_ausland_CH_logsum_tagesreise.fst` / `_reisemitue.fst` when called with a subgroup-specific `logsum_dt`), `../benzoni_thesis/output/attractivity_indexes.csv`
- **Writes**: whatever the invoking call names — e.g. `results_output/destination_mnl_batch_*.csv`, `results_output/destination_mnl_bootstrap_*.csv`, `results_output/destination_mnl_tagesreise_vs_reisemitue*.csv` — plus Apollo's own per-model `results_output/<modelName>_iterations.csv`, `_output.txt`, `_estimates.csv`, `.rds`. All in the top-level `results_output/` folder, not under `data/`.
- **Does**: defines the reusable MNL destination choice framework (not a single fixed model): `build_destination_data()` samples agents/alternatives and joins EMU + topology + optional attractivity variables; `run_destination_model()` estimates one Apollo MNL and prints a results summary; `run_destination_batch()` runs several specs and saves them together; `run_destination_bootstrap()` repeats a spec with fresh with-replacement agent resamples. Configurable: sample size, choice-set size, attractivity variable subset, whether topology is included, which agent subgroup, which EMU lookup, and (`interact_nationality`) whether every variable gets its own coefficient per nationality group or a single pooled coefficient. When sourced as-is, the bottom of the script runs one example (EMU + topo + 6 attractivity vars, 1,000 agents, 300 alts).
- **Note**: the candidate destination universe (`all_zones`, sampled to build each agent's alternative set) is restricted to `zones_communes.gpkg` rows with `MAKROBEZ_STAAT == "CH"` (~7,966 zones) — `zones_communes.gpkg` now also includes Ausland/LI zones, which have no entry in the CH-only logsum lookup above and are never valid tourism destinations here.
- **Note**: this filter must explicitly exclude `NA` (`MAKROBEZ_STAAT == "CH" & !is.na(MAKROBEZ_STAAT)`) -- unlike `data.table`, indexing an `sf`/data.frame object with a logical vector containing `NA` keeps an all-`NA` row at that position rather than dropping it, so a plain `== "CH"` filter let the one broken empty-geometry zone back into the candidate universe, where it was occasionally sampled as an alternative with no logsum match and crashed Apollo ("utilities ... not finite").
- **Note**: 7 / 7,966 CH zones have no `STALAN2020` topology value (apparently newly-added/reclassified communes) and are also excluded from the candidate universe -- the topology term has no `NA`-handling (unlike the logsum join, which only warns), so sampling one of these as an alternative produced the same "not finite" crash.

### `aggregate_regions.R`
- **Reads**: `data/input/zones_communes.gpkg`, `data/amr101.gpkg`, `../benzoni_thesis/output/attractivity_indexes.csv`, `data/output/tt_ausland_CH_logsum.fst` / `_tagesreise.fst` / `_reisemitue.fst`, `data/erreichbarkeit_tt2023.gpkg`
- **Writes**: `data/output/zone_to_amr101.csv`, `data/output/amr101_population.csv`, `data/output/tt_full_logsum_amr101.fst` (+ `_tagesreise.fst` / `_reisemitue.fst`), `data/output/erreichbarkeit_amr101.csv`
- **Does**: aggregates the zone-level EMU (all three subgroup variants) and Erreichbarkeit up to the 101 AMR regions in `data/amr101.gpkg`, so the destination choice model can optionally use these coarser regions as its choice set instead of individual NPVM zones. Zones are first restricted to genuine CH zones (`MAKROBEZ_STAAT == "CH"`, 7,966 / 8,719), then each is assigned to the AMR region with which it shares the **largest overlapping area** (`st_join(..., largest = TRUE)` on the zone/region polygons, not just the zone's centroid; only 1 / 7,966 CH zones has no polygon overlap with any AMR region and falls back to nearest-polygon). Aggregation is a population-weighted average of each variable over the zones within a region, using each zone's resident population (`v02_resident_population`) as the weight; zones missing from the Benzoni population data (1 / 7,966) get weight 0.
- **Note**: the CH filter uses `MAKROBEZ_STAAT`, not canton code (`KTKZ`) — `KTKZ` is `NA` for 7 genuine CH zones in addition to the Ausland/LI zones, so it would wrongly exclude those 7. An earlier version of this script used `KTKZ`, which was a harmless no-op against the original CH-only `zones_communes.gpkg` but became a latent bug once that file was updated to also include Ausland/LI zones.
- **Note**: consumed by `04_destination_choice_amr.R`, a separate script from `04_destination_choice.R` (see below) — the zone-level framework itself was not modified to use regions.

### `compute_zone_shares.R`
- **Reads**: `data/output/zone_to_amr101.csv`
- **Writes**: `data/output/zone_prob_given_region.csv` -- `npvm_id`, `BAE2018`, `BAE2018_fr`, `population`, `region_population`, `zone_share`
- **Does**: computes P(zone | region) for every zone, as its share of its AMR region's total resident population (`zone_share = population_zone / region_population`) -- a proxy for the probability a specific zone is the destination, given that its region was already chosen. Intended to disaggregate a region-level destination choice probability from `04_destination_choice_amr.R` back down to individual zones: `P(zone) = P(region) * P(zone | region)`. Zones with zero population get `zone_share = 0`; shares sum to 1 within every region (checked with `stopifnot`).

### `04_destination_choice_amr.R`
- **Reads**: `data/output/agqpv.csv`, `data/output/zone_to_amr101.csv`, `data/output/amr101_population.csv`, `data/output/erreichbarkeit_amr101.csv`, `data/output/tt_full_logsum_amr101.fst` / `_tagesreise.fst` / `_reisemitue.fst` (all built by `aggregate_regions.R`)
- **Writes**: `results_output/destination_mnl_amr_tagesreise_vs_reisemitue_pop_erreichbarkeit.csv`, plus Apollo's own per-model `results_output/<modelName>_iterations.csv`, `_output.txt`, `_estimates.csv`, `.rds`
- **Does**: a variant of the `04_destination_choice.R` framework where the choice set is the 101 AMR regions instead of individual NPVM zones. Because there are only 101 regions, every agent's full choice set is used — no McFadden alternative sampling, unlike `04_destination_choice.R`. Each respondent's chosen alternative is the AMR region containing their real destination zone (`zone_to_amr101.csv`); only the destination side is aggregated to regions, origin stays a zone. `build_destination_data_amr()` / `run_destination_model_amr()` mirror the zone-level framework's structure (same `interact_nationality` toggle, same coefficient-naming and printing conventions) but are separate, self-contained functions rather than shared code, since the region-keyed joins (`BAE2018` region codes, no alternative sampling, no topology) differ enough from the zone-keyed ones to make a shared implementation more error-prone than two parallel ones. When sourced as-is, the bottom of the script runs one example (EMU + population + Erreichbarkeit, nationality-interacted, full sample, both Tagesreise and Reise mit Ü. subgroups).
- **Note**: `BAE2018` region codes are zero-padded strings (e.g. `"01012"` for Genève) — every `fread()` of a column containing them uses `colClasses = c(BAE2018 = "character")` to avoid silently losing the leading zero (R's default CSV type-guessing would otherwise parse it as integer `1012`, breaking the join against the `.fst` files, which keep it as character throughout since they never round-trip through CSV).
